- **Auth runtime (self-hosted):** set `AUTH_TRUST_HOST=true` (and `trustHost: true` in auth.config) or Auth.js throws `UntrustedHost` behind localhost/proxy. The allowlist (`ALLOWED_SIGNIN_EMAILS`) is checked at link-request time, so non-allowlisted emails never receive a magic link. JWT session strategy so middleware authorizes at the edge without a DB hit. First user to sign in is promoted to ADMIN.
- **Git note:** the user's global `~/.gitconfig` has a malformed empty `gpg.format` that aborts `git commit`/`git log`. Worked around with `GIT_CONFIG_GLOBAL=/dev/null` + explicit identity; their global config was left untouched.

This pulls Spec §8 (self-host containerization) forward from Phase 8; Phase 8 will refine for production (smaller image / standalone, secrets, healthchecks). Gotchas captured: single build owner avoids the shared-tag race; `INNGEST_DEV=http://inngest:8288` keeps the worker on the local dev server (no signing key) under `NODE_ENV=production`.
- **Provider routing:** text generation now defaults to OpenRouter (`OPENROUTER_API_KEY` in env) with an on-demand catalog sync into Settings; image generation is configured for Gemini (`GEMINI_API_KEY`) with `gemini-3.1-flash-image` as the default image model. Provider secrets stay in `.env`, not the Setting table.
- **Strapi integration:** `CmsType.STRAPI` is available with encrypted Content API token storage, configurable collection API ID, field mapping, content format (`HTML`, `MARKDOWN`, or basic Strapi blocks), and draft/published create mode. The Strapi publisher helper posts to `/api/:pluralApiId` with a Content API bearer token; the full human approval → publish workflow is still Phase 4.
- **Edit a published article → republish updates in place:** editing (or regenerating) a PUBLISHED article now sends it back through the review gate (`updateArticleDraft`/`regenerateArticleDraft` set `PENDING_REVIEW`), and on the next publish, `publishArticleToCms` looks up the latest successful `PublishRecord` and passes its `cmsPostId` (the Strapi v5 `documentId`) to `publishToStrapi`, which **PUTs `/api/:plural/:documentId`** instead of POSTing a new entry — so the enhance → review → republish loop updates the live post rather than creating duplicates. The publish button reads "Republish (update live post)" once a successful publish exists; the audit records `updated: true`. Human gate preserved (re-approval required before republish). Known limitation: images are re-uploaded to Strapi media on each republish (old media is orphaned, not pruned).
- **Editable primary keyword (refinement):** the keyword (SEO target) was fixed at draft time and often ended up being a headline, skewing every keyword check. `updateArticleKeyword` lets the reviewer set a concise target from the review UI ("Primary keyword" card); it updates `Keyword.term`, re-scores against the new keyword, and audits (`article.keywordUpdated`). Unique per site — a term already used by another keyword is rejected. The keyword term is now exposed on `ArticleDTO` (read paths + draft creation include it). This is the "refine" lever on top of the automated pipeline (draft → auto category/tags → in-body image suggestions → SEO score): set a sharper keyword → re-score → regenerate.
- **SEO scorer hardened for long-tail / headline keywords:** when an article's stored "keyword" is actually a headline (the real case: `keyword.term` = the full title), the keyword checks were impossible to satisfy — a 90-char phrase can't fit a 50–60 char title and never repeats, so `keyword-in-title` (critical) failed, density read 0.0%, and a solid article scored `fail`. The regenerator faithfully forwarded these unsatisfiable "issues," so it looked like it ignored SEO. Fixed in `seo-score.ts`: `isLongKeyword` (>4 significant words or >50 chars) switches keyword matching to term-overlap (≥60% of significant words for title/slug/intro; ≥2 topic words for a heading) and skips exact-density (not a meaningful signal for long-form). Short keywords are unchanged (still require every significant word). The existing article re-scored 86/fail → 100/pass. Deeper cause is data: the keyword should be a concise phrase, not a headline — keyword editing is a sensible follow-up.
- **Iterative regeneration (comments + SEO feedback):** `regenerateArticleDraft` rewrites an existing article with the LLM, feeding back the current draft, the reviewer's free-text comments, and the concrete SEO findings (the failing/weak checks from the stored report, or a freshly computed one) so each pass is stronger. Implemented by extending the drafting prompt with an `ArticleRevisionContext` ("improve the existing draft" framing + current content + comments + SEO issues to fix) rather than a separate code path. It preserves the reviewer's taxonomy and any in-body images, re-scores, increments `regenAttempts`, writes a new AI `ArticleRevision`, returns the article to `PENDING_REVIEW`, and audits `article.regenerated`. Human-triggered (a "Regenerate (AI)" card on the article page) and **never auto-publishes** (Spec §10.1); blocked for PUBLISHED/PUBLISHING. Not capped by `max_regen` (that bound is for the future autonomous Phase 5 QA loop, not deliberate human regeneration).
- **LLM auto-assigns category + tags:** at draft time `generateArticleDraft` fetches the site's existing Strapi taxonomy (`listSiteTaxonomy`, best-effort — never blocks drafting) and passes the available categories/tags to the drafter prompt; the model returns `categorySlug` (single best fit) + `tagSlugs` (2–5) in its structured output. The service validates the choices against the fetched slug sets and stores only existing ones — hallucinated/unknown slugs are dropped (no auto-create), matching the existing-only policy. The reviewer's picker stays and is pre-filled with the model's choices for override. Non-Strapi sites or unreachable CMS → no options offered, no selection (reviewer can still pick later). **Existing/pre-feature articles** (drafted before auto-assignment) can be classified on demand without rewriting content via `autoAssignArticleTaxonomy` (a focused LLM classification over the article title/content + available taxonomy), surfaced as an "Auto-assign category & tags" button on the article page; choices are validated to existing slugs and audited (`article.taxonomyAssigned`).
- **Inline-image publishing + category/tag relations (Strapi v5):** publishing now embeds in-body images into the article body and connects taxonomy. On publish, each `ArticleImage` that has an asset is uploaded to Strapi media and embedded into the Markdown `content` as `![alt](url)` under its placement heading (`embedInlineImagesIntoMarkdown`), so images render inline (works when the site's content format is **Markdown** — matches Strapi richtext). The reviewer picks a **category** (single) + **tags** (multi) in the review editor, populated live from Strapi via `listSiteTaxonomy` (`fetchStrapiCollection`); selections are stored as slugs on the article (`Article.categorySlug`, `Article.tagSlugs[]`, migration `20260615110940_add_article_taxonomy`) and resolved to Strapi v5 **documentId**s at publish (`resolveDocumentIdsBySlug`), then connected via `{ connect: [{ documentId }] }` (category oneToOne) / array (tags manyToMany). **Existing taxonomy only**, matched by slug — unknown slugs are skipped, never auto-created. `StrapiCredentials` gained `categoryApiId`/`tagApiId` (default `categories`/`tags`) and `fieldMap.category`/`fieldMap.tags` (default `category`/`tags`), all matching the owner's schema so no reconfiguration is needed. Per owner's Strapi: v5.36.1, body field `content` (richtext-as-Markdown), cover `image`, relations `category` (oneToOne) + `tags` (manyToMany). Deferred: auto-creating missing taxonomy (off until explicitly enabled); HeroSlide publishing.
- **In-body (supporting) images:** the drafter previously produced a single hero `imagePrompt` blob, and the pipeline supported exactly one image (one upload slot, one published image), so longer articles got no in-body visuals or per-image prompts. Now the drafter returns a structured plan: the hero `imagePrompt` plus `inlineImages[]`, where each in-body image carries `placement` (the heading it belongs under), `alt`, `aspectRatio`, and its own standalone prompt — added only where a visual genuinely aids comprehension (empty for short/simple posts; no decorative filler; no placeholders inside `contentMarkdown`). New `ArticleImage` model (migration `20260612172001_add_article_images`) stores each in-body image with an optional uploaded/generated asset; service adds `listArticleImages`, `uploadArticleInlineImage`, `generateArticleInlineImage` (Gemini, same model as the hero), and the SEO scorer gains an `inline-images` check that warns when a long article (≥1200 words) plans none. The article review page lists each in-body image with its placement, alt, aspect ratio, copyable prompt, and per-image generate/upload. The hero image flow is unchanged. Deferred (the "Full inline publish" option, Phase 4+): embedding the in-body images into the article body and pushing them to the CMS on publish — depends on per-site Strapi media field/relation config. Per owner decision: plan + per-image upload (no auto inline-publish yet).
- **SEO scoring + flagging (advisory):** added a deterministic, people-first SEO scorer in `packages/core/src/seo` (`seo-score.ts` + Zod `seo-report.ts`) that encodes the *mechanical* rules from the SEO skill (`docs/ai-project`: seo-article-rules Step 4–5, quality-review-checklist) — title/slug/meta shape, heading structure, keyword placement + density, snippet-friendly formatting, internal/external links, anti-patterns (generic openers, hype/filler, site-banned phrases), and image-prompt quality. It returns `{ version, score 0–100, verdict pass|warn|fail, checks[], flags[], wordCount, generatedAt }`, stored in the **existing** `Article.qaReport` Json column (no migration) and surfaced read-only on the article review page (`SeoScoreCard`). Scoring runs automatically on draft generation and on every human edit, and is **advisory only** — it never changes article status or the human approval gate (Spec §10.1). Drafting is now SEO-aware: `SEO_DRAFTING_RULES` (aligned with the scorer) is injected into the drafting system prompt and the output spec asks for direct-answer intros, keyworded H2s, lists/tables, internal-link suggestions, and sourced claims. **Existing articles** (drafted before this) start with no in-body images; `suggestArticleInlineImages` runs the LLM over the existing content to propose them on demand (surfaced as a "Suggest in-body images (AI)" button on the article's empty in-body-images card), creating one row per suggestion and refreshing the SEO in-body-image check. It only runs when the article has none yet (guard), and is audited (`article.inlineImagesSuggested`). Deliberately out of scope (deferred to Phase 5): the LLM-assisted editorial rubric (business fit, originality, E-E-A-T depth, risk), `QA_FAILED` auto-transitions, and bounded regeneration. Per owner decision: deterministic-only engine, flag-for-reviewer (no gate change).
- **Trending-topic discovery → keyword queue (Phase 6, partial):** per-site discovery that pulls candidate keywords from three pluggable sources behind a `KeywordSource` interface (`packages/core/src/keyword-sources`) and enqueues them as QUEUED keywords with provenance + a 0–1 ranking score — never drafts/publishes (gate intact). **Research-verified (2026):** Google Trends still has **no usable public API** (official one is closed-alpha, interest-over-time only; `pytrends`/`google-trends-api` are dead/429-blocked) — so the sources are: (1) **GoogleSearchConsoleSource** (primary, free) — service-account JWT (hand-rolled with node:crypto, read-only `webmasters.readonly`), `searchAnalytics.query` for striking-distance (pos 5–20 + impressions) and rising (28d vs prior-28d) signals; (2) **googleTrendsRssSource** — free Trending-Now RSS (geo-only) through the SSRF guard, filtered to the site's niche by an LLM relevance pass; (3) **llmWebTrendSource** — OpenRouter web plugin (`plugins:[{id:'web'}]`), untrusted-data handling. - **Cost/usage accounting + budget guard (Phase 2/7, the previously-missing non-negotiable):** every paid LLM/image call now writes a `UsageRecord` (provider/model/purpose/tokens/costUsd) and is preceded by `assertWithinBudget` (`packages/core/src/cost/usage.ts`). Text cost comes from the synced OpenRouter `Settings.pricing` (USD/MTok, splitting fresh vs cached input tokens); image cost from a new `Settings.image_pricing` (flat USD/image, seeded `gemini-3.1-flash-image: $0.039`). - **HTTP security headers (Phase 7, partial):** `apps/web/next.config.ts` now sets `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` everywhere, plus a pragmatic `Content-Security-Policy` (script/style `'unsafe-inline'` for Next's hydration runtime only — no app-authored inline scripts; `img-src` allows `data:`/`blob:`/`https:` for base64 + remote CMS images; `connect-src` allows Sentry incl. region ingest hosts) and HSTS **in production only** (dev HMR untouched; HSTS assumes TLS at the reverse proxy). - **Autopilot: unattended production up to the review gate (Phase 6):** the pipeline previously dead-ended at QUEUED keywords — nothing consumed them, so every article cost 7+ dashboard clicks. Now a fixed `*/15` **`pipeline-tick`** cron reads all cadence from Settings at runtime (Inngest cron strings are static and only re-register on restart, so cadence CANNOT live in the cron; the rule adopted is **Inngest flow control expresses safety, Settings express policy**), decides per site via the pure `decidePacing` (`packages/core/src/pipeline/pacing.ts`, 26 unit tests), and claims at most **one** keyword per site per tick. That cap is structural: it bounds worst-case budget overshoot to a single article and makes a pacing bug incapable of fanning out many paid drafts. The tick emits `scribe/keyword.claimed`; **`article-autodraft`** (concurrency 1/site, `idempotency: event.data.keywordId`) drafts and then enriches inline — taxonomy, hero image, in-body images — each step best-effort so the article always reaches PENDING_REVIEW, and each independently re-checking the per-article budget. `discovery-run` (rate-limited 1/24h per site) tops the keyword buffer up on demand, and `review-digest` emails what is waiting. **Decisions:** the weekly target is **per site** (global default + `Site.autopilotArticlesPerWeek` override) and **counts human-made articles too**, because it is a cost budget rather than an automation quota (excluding them would let output reach 2N against a $50/mo budget); the backlog cap counts PENDING_REVIEW **plus** CHANGES_REQUESTED, so production stops on its own for a reviewer who has stopped reviewing; failed drafts terminate at `KeywordStatus.SKIPPED` (never back to QUEUED, which would re-claim an undraftable keyword 96×/day) with a dashboard Requeue; a **budget reserve** (default 10%) stops the tick before claiming, since `assertWithinBudget` is a documented soft pre-check and without it the autopilot would eat the last dollar the human needs to fix a draft. Claiming is a raw `FOR UPDATE SKIP LOCKED` UPDATE (`claimNextKeyword`) — the one place raw SQL is justified, because DB-level atomicity IS the behaviour; proven by an integration test firing 5 concurrent claims and asserting 5 distinct ids. Migration `20260828120000_add_autopilot`.

- **Approve now publishes, and the human gate got stronger (Phase 4/6):** approving emits `article.approved`; **`publish-run`** consumes it and re-verifies the human at the publish step, exactly as Spec §10.1.1 prescribes. **This closed a latent hole:** `SYSTEM_ACTOR` carries role ADMIN, so `authorize(SYSTEM_ACTOR, 'article.publish')` returned cleanly and was the *only* actor check `publishArticleToCms` performed — not exploitable before, but one careless line away once cron code creates articles. New `assertHumanPublishActor` (`packages/core/src/auth/human-actor.ts`) rejects reserved ids, requires a real User row, re-reads the role from the DB (closing a stale-JWT window, since Auth.js only re-reads the role at sign-in), and on the event path requires a `reviewId` matching an APPROVED Review whose `reviewerId` FK only an authenticated session can write. **The payload's `actorId` is treated as a forgeable claim; `reviewId` is the load-bearing evidence.** It mints a `PublishGrant` branded with a module-private Symbol — a real capability token, never serialized — and `transitionArticle` requires one to reach PUBLISHING/PUBLISHED. Denials are audited with `actorId: null` (a forged id there would raise the AuditLog→User FK and destroy the signal) and mapped to `NonRetriableError` so a security denial is never retried 4×. Publish stays **ADMIN-only**: CLAUDE.md §10.1 says "Admin/Editor" but `authorize.ts` and its test say ADMIN, and the owner is the sole account — an EDITOR's approval parks at APPROVED. The Publish button survives as the **recovery** path (failed publishes, or an approved article with no settled record for its version), not the happy path.

- **`transitionArticle` now exists, partially adopted (pre-existing violation, Phase 6):** CLAUDE.md and `schema.prisma`'s header both asserted it existed; all 8 status writes were raw `prisma.article.update`. With a machine driving the pipeline this stopped being tidiness — `approveArticle` had **no from-state validation**, so REJECTED→APPROVED and PUBLISHED→APPROVED both silently succeeded, and under publish-on-approve an accidental Approve on a published article would fire a republish. `packages/core/src/domain/article-transitions.ts` adds a deny-by-default table encoding both legality and actor class, guarded by a **property test asserting no `system`/`any` rule targets APPROVED, PUBLISHING, or PUBLISHED** — an invariant that survives future edits by people who never read this entry. Updates use `where: { id, status: from }` as an optimistic-concurrency guard, so a double-clicked Approve fails with P2025 instead of clobbering. **Adopted for:** APPROVED, PUBLISHING, PUBLISHED, PUBLISH_FAILED, the three review decisions, and the edit-after-approval revert (previously a *silent* status change with no audit row — now that approval implies publishing, that silence was the whole difference between published and not). **Remaining debt:** draft creation (`:385`, a create, not a transition) and `regenerateArticleDraft` still write status directly.

- **Two blockers found and fixed before the autopilot could work (Phase 6):** (1) all 10 `recordAudit` calls in `article-service.ts` hardcoded `actorId: actor.id, actorType: 'human'`; `SYSTEM_ACTOR.id` is the string `'system'` and `AuditLog.actorId` is an FK to `User.id`, so **the first automated draft would have raised P2003 and rolled back `createDraftRecords` — no article, ever** — while also mislabelling cron work as human (§10.1.6). Fixed with `auditActorFields` in the new `packages/core/src/auth/system-actor.ts`; a User row named "system" was deliberately NOT created, since that would hand the cron a human identity and dissolve both the audit guarantee and the publish guard. (2) `generateArticleDraft` ran the keyword through `parseKeywordSeedList`, which since `0350694` splits on commas — a discovered term containing one would draft only the fragment and upsert a *different* Keyword row, orphaning the claim in IN_PROGRESS forever while the pacing counter still incremented. The automated path is now id-based (`keywordId`), leaving the human free-text path untouched.

- **Publish idempotency was decorative, now real (Phase 4 fix):** the key was `article:{id}:{randomUUID()}` — fresh per attempt, so the `@unique` constraint on `PublishRecord.idempotencyKey` could never fire, contradicting the documented `publish:{articleId}:{currentVersion}` rule. Harmless while a human chose to retry; a genuine duplicate-post risk once Inngest retries automatically and invisibly (CMS POST succeeds, response never arrives, retry POSTs again). Now deterministic, with a success fast-path, **claim-then-publish** (the row is written as `pending` in the same transaction that sets PUBLISHING, so a retry collides instead of double-posting), and an upsert that permits retrying a `failed` row at the same version. The version-agnostic prior-success lookup is deliberately kept, since it is the only thing that catches legacy `article:{id}:{uuid}` records.

- **Inngest could never fire locally, silently (infra fix):** `docker-compose.yml` pointed the dev server at `http://worker:3100/api/inngest`, which only resolves inside the compose network — but the documented fast path is `docker compose up -d postgres inngest` + `pnpm dev`, where no worker container exists. Registration is *inbound*, and crons only fire for registered functions, so **zero functions registered and the dev UI simply showed no apps**. A second, opposite failure: compose publishes the dev server on host 8289 while the SDK's dev default is 8288, so host-run `inngest.send()` posted into the void. Fixed with `host.docker.internal:4100` (the worker's published port in *both* modes) plus `extra_hosts` for Linux parity, and `INNGEST_DEV=http://localhost:8289` in `.env.example`.

- **No brief stage (conscious deviation):** CLAUDE.md describes keyword→brief→draft, but no code has ever written a `Brief`; the model, `BriefStatus`, `Site.briefAutoApprove` and `briefs_per_run` are all unused. `generateArticleDraft` goes keyword→draft in one call, so the autopilot does too. Recorded here so it is not mistaken for an oversight.

- **Production deploy path (Phase 8):** a single Ubuntu VPS running `docker-compose.prod.yml`. CI builds the image on GitHub and pushes it to GHCR (`ghcr.io/<owner>/scribe:sha-<commit>` + `:latest`); the **Deploy** workflow chains on `workflow_run` of CI for `main`/`master`, so a red CI never ships, then scp's the compose file + Caddyfile and SSHes in to pull, migrate (one-shot `migrate` service via `depends_on: service_completed_successfully`) and `up -d`. The VPS never runs `next build`. The release tag is pinned into `/opt/scribe/.env` (`IMAGE`/`IMAGE_TAG`) so a manual `docker compose up -d` restarts the same image rather than drifting to `:latest`; rollback is editing that tag. Caddy terminates TLS (Let's Encrypt) and is the only published service besides SSH; the Inngest UI (no auth) binds to `127.0.0.1:8288` and is reached over an SSH tunnel. Inngest runs `inngest start` with SQLite persistence on a volume and the same `INNGEST_EVENT_KEY`/`INNGEST_SIGNING_KEY` (hex) the SDK uses, syncing the worker via `--sdk-url http://worker:3100/api/inngest`; `INNGEST_DEV=0` is forced in compose so a copied dev `.env` cannot put production into dev mode. The VPS pulls the private GHCR package with the run's ephemeral `GITHUB_TOKEN` (no long-lived registry secret on the box). With no `VPS_HOST` secret the deploy job is skipped and the image is still pushed, so merging is safe before the server exists. Deferred: slim standalone image, external Redis/Postgres for Inngest state, SHA-pinned actions (Phase 7).
